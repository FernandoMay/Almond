\section{Executive summary}
Almond is the backend, core-engine, and local operations-dashboard MVP for Jornada40. It transforms deterministic hourly visitor demand, employee availability, and MXN hourly rates into an explainable schedule. The implementation is a small Python vertical slice: data generation, demand calculation, a CP-SAT optimizer, independent verification, baseline analysis, schedule-derived economics, a JSON command-line demo, and a static FastAPI-served UI.

\callout{\textbf{Current answer.} The reproducible demo reaches 100\% modeled and peak coverage with an optimized cost of 16,402 MXN. Its documented current policy costs 26,950 MXN, also covers 100\% overall and at peak, and records 109 overstaffed person-hours plus 70 overtime hours. The schedule-derived delta is \textbf{10,548 MXN avoided} or \textbf{39.14\% savings}; the optimized schedule has no verifier violations. The challenge target is \textbf{at least 8\%}, while this implementation computes the result from the two schedules and configured rates.}

\section{Business problem and product scope}
Retail or service operations need to translate hourly demand into staffing decisions without hiding feasibility failures or overstating financial impact. The first product question is deliberately narrow: \emph{how many people are needed each hour, what schedule satisfies that demand, and what does it cost?}

The MVP accepts synthetic hourly visitors, employee availability, and fixed hourly rates. It returns a candidate schedule, constraint evaluations, independent verification, coverage metrics, and a comparison with a deterministic current schedule. The system is an engine, not a production workforce-management product.

\subsection{In scope}
\begin{itemize}
  \item One generic employee role and integer hourly demand.
  \item Seven modeled days with opening hours 08:00--18:00 in the demo; validated new-store requests may provide a shorter horizon and opening interval.
  \item Fixed hourly MXN rates and per-day availability windows.
  \item One contiguous interval per employee per day.
  \item A current schedule versus optimized schedule flow.
  \item Explicit uncovered demand rather than silent infeasibility.
\end{itemize}

\subsection{Out of scope at this commit}
Breaks, skills, absences, payroll integration, persistence, authentication, deployment, production hardening, asynchronous job storage, and configurable shift rules are \planned. The local API and dashboard are implemented; they are not a deployed service. Explicit peak coverage, overtime economics, and configurable objective weights are implemented.

\section{Data model and deterministic synthetic scenario}
The principal immutable records are:
\begin{itemize}
  \item \texttt{Employee(id, hourly\_cost\_mxn, availability)};
\item \texttt{DemandPoint(day, hour, demand, visitors, peak)};
  \item \texttt{Scenario(employees, demand, days, open\_start, open\_end, optimization)};
  \item \texttt{Assignment(employee\_id, day, start, end)}, with end exclusive;
  \item \texttt{Schedule(assignments)}, with per-employee hour aggregation.
\end{itemize}

The demo uses \texttt{random.Random(40)}. It creates seven employees, E1 through E7, with rates from 58 to 82 MXN/hour in four-MXN increments. Every employee is available from 08:00 through 18:00 on each of seven days. For day $d$ and hour $h$, visitors are generated as
\[
V_{d,h}=10+2(h-8)+3(d\bmod 3)+\operatorname{randint}(0,5),
\]
and required staff is
\[
R_{d,h}=\max\left(1,\left\lceil\frac{8V_{d,h}}{60}\right\rceil\right).
\]
Hours are integer buckets; all intervals use $[\text{start},\text{end})$ semantics and all costs are integer MXN amounts.

The generated current policy keeps a fixed five-person floor for the full 08:00--18:00 opening interval and rotates the employees deterministically by day. This is an explicit observed-policy assumption: it is operationally simple, availability-checked, and intentionally inefficient through rigid coverage. It is not selected to produce a desired savings percentage. Removing or changing the floor changes the comparison, not the optimizer's hard constraints.

The demo's peak rule is explicit and testable: every demand bucket with $12\le h<16$ is marked peak; all other modeled hours are normal.

\section{Solver formulation}
\subsection{Decision variables}
For employee $e$, day $d$, and modeled hour $h$:
\[
x_{e,d,h}\in\{0,1\},\qquad x_{e,d,h}=1\text{ iff employee }e\text{ works hour }h.
\]
For every demand bucket:
\[
0\le u_{d,h}\le R_{d,h},
\]
where $u_{d,h}$ is explicit uncovered demand.

\subsection{Hard constraints}
\textbf{Weekly hours.} For every employee, $\sum_{d,h}x_{e,d,h}\le40$.

\textbf{Availability.} If $h$ is outside the employee's daily window, $x_{e,d,h}=0$.

\textbf{Coverage accounting.} Each bucket satisfies
\[
\sum_e x_{e,d,h}+u_{d,h}\ge R_{d,h}.
\]
The slack variable makes shortage explicit and bounded rather than allowing a hidden invalid result.

\textbf{Daily contiguity.} At most one start variable is allowed for an employee/day. A later worked hour requires continuity from the previous hour or a start at that hour. This prevents two separated intervals from being represented as one daily assignment.

\subsection{Objective and deterministic settings}
The implemented objective is
\[
\min\left(w_l\sum_{e,d,h}x_{e,d,h}c_e+w_n\sum_{(d,h)\notin P}u_{d,h}+w_p\sum_{(d,h)\in P}u_{d,h}\right),
\]
where $c_e$ is the employee's hourly MXN rate, $P$ is the explicit peak set, and the default weights are $(w_l,w_n,w_p)=(1,10000,20000)$. Peak buckets are hard-covered when feasible; an infeasible hard model falls back to bounded explicit slack. OR-Tools CP-SAT is configured with \texttt{num\_search\_workers = 1} and \texttt{random\_seed = 40}. The CLI reports the exact solver status; the current run is \texttt{OPTIMAL}.

For arbitrary schedule economics, with weekly threshold $T$ and multiplier $m$, regular hours are $\min(H_e,T)$, overtime hours are $\max(H_e-T,0)$, and employee cost is $\text{regular}\times c_e+\text{overtime}\times c_e\times m$. Defaults are $T=40$ and $m=1.5$; the optimizer retains a hard 40-hour cap.

\section{FastAPI product surface}
The first HTTP surface is implemented as a thin boundary over the verified core. It exposes the following exact routes:
\begin{itemize}
  \item \texttt{GET /health} returns the stable JSON object \texttt{"status":"ok","api\_version":"v1"}.
  \item \texttt{GET /v1/demo} runs the default seed-40 demo and returns the same shape as the CLI.
  \item \texttt{POST /v1/optimize/demo} accepts an optional JSON \texttt{seed} (non-negative integer, default 40) and returns the same result shape.
  \item \texttt{POST /v1/optimize} accepts a typed store scenario and returns the same result shape plus a stable \texttt{scenario} metadata block.
  \item \texttt{GET /} serves the dependency-light dashboard; \texttt{/static/styles.css} and \texttt{/static/app.js} provide its local assets. The UI runs the demo, accepts one JSON scenario upload, presents current-versus-optimized metrics and constraint explanations, and downloads the demo schedule. CSV upload and uploaded-scenario schedule download are not exposed by the UI.
\end{itemize}
The new-store request contains non-empty \texttt{employees} and \texttt{demand}, a bounded \texttt{horizon}, unique employee IDs, unique demand \texttt{(day,hour)} slots, integer MXN rates, per-day \texttt{[start,end)} availability, visitor counts, and explicit \texttt{required\_staff}. Objective weights, overtime configuration, and baseline policy are optional. Duplicate or out-of-range input produces normal FastAPI 422 responses. The route translates the request into immutable domain objects and calls \texttt{cli.run\_scenario(scenario)}; solver, verification, and economics logic is not duplicated. A minimal reproducible request is:

\begin{verbatim}
{"employees":[{"id":"A1","hourly_rate_mxn":100,
  "availability":{"0":{"start":8,"end":10}}}],
 "demand":[{"day":0,"hour":8,"visitors":8,"required_staff":1}],
 "horizon":{"days":1,"opening_hour":8,"closing_hour":10},
 "baseline_policy":{"staffing_floor":1,"shift_start":8,"shift_end":10}}
\end{verbatim}

The complete JSON request or exact-schema CSV bundle is the reproducibility input. Repeating either with the fixed single-worker, seed-40 CP-SAT configuration produces byte/semantic-equivalent JSON and schedule CSV. The \texttt{almond-api} console script starts Uvicorn on the local development address, and \texttt{GET /} serves the local dashboard. The UI calls \texttt{GET /v1/demo}, \texttt{POST /v1/optimize/json-file}, and \texttt{GET /v1/demo/schedule.csv}; it does not expose CSV upload or retain uploaded scenarios. Persistence, authentication, deployment, asynchronous job storage, and production hardening remain planned.

\section{Operational command-line file workflow}
The local CLI provides a synchronous batch boundary that does not make API calls. The no-argument command remains the compatibility path:
\begin{verbatim}
.venv/bin/almond
\end{verbatim}
It prints the seed-40 demo result JSON. The explicit optimization command accepts either the validated JSON scenario form:
\begin{verbatim}
.venv/bin/almond optimize --json-file scenario.json \\
  --result-json result.json --schedule-csv optimized.csv
\end{verbatim}
or the complete CSV bundle form:
\begin{verbatim}
.venv/bin/almond optimize --employees employees.csv \\
  --availability availability.csv --demand demand.csv \\
  --days 1 --opening-hour 8 --closing-hour 10 \\
  --result-json result.json --schedule-csv optimized.csv
\end{verbatim}
The JSON input is the same object accepted by \texttt{POST /v1/optimize/json-file}. The CSV files use exact headers \texttt{id,hourly\_rate\_mxn}, \texttt{employee\_id,day,start,end}, and \texttt{day,hour,visitors,required\_staff,peak}; horizon flags define the modeled interval. The command reuses \texttt{parse\_json\_bytes}, \texttt{parse\_csv\_bundle}, \texttt{OptimizeRequest}, \texttt{build\_scenario}, \texttt{run\_scenario\_with\_schedule}, and \texttt{schedule\_csv}; it does not duplicate solver or economics logic.

Both output paths are optional. \texttt{--result-json} writes the complete existing result object with sorted keys, two-space indentation, and a final newline. If it is omitted, that JSON is printed to stdout. \texttt{--schedule-csv} writes only optimized assignments with the stable header \texttt{employee\_id,day,start,end,hours}, sorted by day, start, end, and employee ID. If it is omitted, no schedule file is created. Requested parent directories are created only when needed. Invalid combinations and malformed input exit with code 2 and a concise actionable error without a traceback. The boundary is local and synchronous; authorization, persistence, deployment, and asynchronous job storage remain planned.

\section{Baseline, current schedule, and economics}
\subsection{Formulas}
For an assignment $a$, hours are $a.end-a.start$. Schedule cost is
\[
C(S)=\sum_{a\in S}\operatorname{hours}(a)\,c_{\operatorname{employee}(a)}.
\]
Coverage percentage is demand-weighted capped coverage:
\[
\operatorname{Coverage}(S)=100\times
\frac{\sum_{d,h}\min(\operatorname{coverage}_S(d,h),R_{d,h})}
{\sum_{d,h}R_{d,h}}.
\]
Avoided cost and savings are
\[
A=C_{current}-C_{optimized},\qquad
P=100\times\frac{A}{C_{current}}.
\]
The implementation returns zero percentage when the current cost is zero.

\section{Independent verification and validation}
The verifier is a separate module and checks every returned assignment for:
\begin{itemize}
  \item known employee identity;
  \item non-empty interval and availability containment;
  \item overlap or duplicate assignment for the same employee and day;
  \item no more than 40 aggregate weekly hours;
  \item coverage at every demand bucket.
\end{itemize}

Baseline analysis applies the same operational checks for current schedules, while deliberately ignoring unknown employee IDs when calculating cost rather than raising a key error. It still reports the unknown ID as a violation. This makes bad input visible and keeps diagnostic analysis safe.

\section{AI-assisted engineering log}
The project used bounded AI-agent work units with human review between them. One implementation writer created the initial vertical slice; an independent verifier inspected the result; a correction writer fixed the confirmed overlap defect; later writers added baseline economics, peak/overtime/objective behavior, the demo API, the validated new-store API, stateless file adapters, the operational CLI, and this local dashboard. The current work unit preserves the no-argument command, adds a presentation surface over verified API results, and emits no new domain decisions or solver behavior.

The human owner retained authority over product scope, modeling assumptions, acceptance of findings, commit boundaries, and repository delivery. Agents did not commit or push changes. The work-unit prompts required exact test and runtime commands, and the parent reviewed the returned evidence before committing.

Independent review boundaries are concrete rather than rhetorical: the verifier is separate from the solver, regression tests exercise invalid availability, overlap, unknown employees, economics, deterministic generation, and zero-cost safety, and the CLI exposes the evidence. The repository history and tests specifically preserve defects around overlap/duplicate assignments and unknown employee cost handling as regression coverage. These checks validate software behavior; they do not validate labor law, payroll, wage accuracy, or operational policy.

The human owner remains responsible for legal interpretation, service-time assumptions, wage data, operational availability rules, and production use of schedules. Passing automated tests is not legal or payroll approval.

The decisive solver prompt recorded by the project is:
\begin{quote}
Given hourly demand and employee availability, choose binary hourly assignments that minimize MXN labor cost plus uncovered-demand penalty. Enforce availability, at most one contiguous interval per employee per day, and no more than 40 weekly hours. Return a schedule that an independent verifier can inspect.
\end{quote}

\section{Engineering decisions, limitations, risks, and roadmap}
\subsection{Decisions}
\begin{itemize}
  \item Keep domain dataclasses independent from OR-Tools.
  \item Use deterministic seed and single-worker CP-SAT settings for reproducible demos.
  \item Make uncovered demand explicit and penalized rather than silently relaxing coverage.
  \item Compare against a plausible current schedule, not a fabricated full-open schedule.
  \item Compute costs from generated assignments and employee rates, including configured overtime premiums for arbitrary schedules.
  \item Keep peak coverage explicit and separately auditable from normal coverage.
  \item Store objective weights in scenario configuration rather than embedding an 8\% savings target.
  \item Validate new-store input at the API boundary, then reuse the exact verified application path used by the CLI and demo API.
  \item Keep the operational CLI file boundary explicit: one JSON scenario or a complete CSV bundle, optional deterministic outputs, and no API dependency.
\end{itemize}

\subsection{Limitations and risks}
The synthetic scenario is not a forecast. Service time is fixed at eight minutes, each employee has one generic role, rates are fixed, and overtime settings are modeling inputs rather than payroll approval. The finite shortage weights are modeling choices, not legal service-level guarantees. The baseline's fixed-floor inefficiency is intentional, so cost-only comparisons are misleading without coverage. Finally, the CLI is not an authorization boundary for production schedules.

\subsection{Roadmap}
The next engineering increments should add breaks, configurable shift rules, and schedule-change penalties while preserving independent verification. API and UI layers should consume domain results rather than recompute validity or savings. Persistence and deployment controls should follow once data contracts and operational approvals exist. A defensible $\ge8\%$ savings scenario should be created only by changing explicit scenario inputs or operational assumptions, documenting the change, and verifying that coverage and constraints remain acceptable; it must never be back-solved from a desired headline.

\section{File workflow and schedule export}
The current work unit adds a stateless file adapter over the validated API. \texttt{POST /v1/optimize/json-file} accepts a UTF-8 \texttt{.json} upload with the documented \texttt{OptimizeRequest} shape. \texttt{POST /v1/optimize/csv} accepts exact headers \texttt{id,hourly\_rate\_mxn}, \texttt{employee\_id,day,start,end}, and \texttt{day,hour,visitors,required\_staff,peak}, plus validated \texttt{days}, \texttt{opening\_hour}, and \texttt{closing\_hour} form fields. Empty files, missing headers, extra columns, duplicates, unknown employees, malformed values, and invalid ranges are rejected before optimization.\par

\texttt{GET /v1/demo/schedule.csv} and \texttt{POST /v1/optimize/schedule.csv} return \texttt{text/csv} with the stable header \texttt{employee\_id,day,start,end,hours}. Rows are sorted by day, start, end, and employee ID and contain only optimized assignments. The local \texttt{almond optimize} command provides the equivalent no-API batch workflow with optional result JSON and schedule CSV paths. The dashboard is a local presentation surface; persistence, authentication, deployment, asynchronous job storage, and production hardening remain \planned. This report documents commit \texttt{590b1bc}.
